# OpsCenter v4.6.2 稳定性与安全审计

审计日期：2026-08-31

审计基线：`v4.6.1` / `1c7306156ff2f654354c828335126d163bec1b44`
审计范围：后端运行时、数据库连接、认证与 API 密钥、服务健康、历史指标、旧版兼容文件、CI 配置。

## 审计原则

- 只把源码、测试、OpenAPI 或线上响应能够证明的事实写入本文。
- 本期只修复能够保持向后兼容的高优先级问题，不重写主程序，不改变主机、日志和监控采集策略。
- 不读取或修改线上密钥；发现仓库曾提交明文值时，只从当前版本移除并要求轮换。
- AI 接口严格只读，不允许执行 SSH、扫描、探活、容器操作、进程信号或数据库写操作。

## 已在 v4.6.2 修复

### 1. AI API 缺少强制认证

原有 `require_api_key()` 为兼容免登录工作台，未携带 Bearer 密钥时直接放行。新的 `/api/v2/ai/*` 不能沿用这一行为。

处理：扩展 API 密钥依赖，AI 路由统一使用 `required=True`。缺少、无效或停用的密钥均返回 401；只接受现有 `read` 或 `write` API 密钥。

### 2. 高频 AI 查询造成 API 密钥写放大

原有密钥校验每次请求都更新 `last_used_at` 并提交事务。AI 高频轮询会把只读查询变成持续数据库写入。

处理：同一密钥的 `last_used_at` 最多每分钟更新一次。密钥校验、停用和 scope 语义保持不变。

### 3. 主程序存在两套数据库连接池

`main.py` 与 `database.py` 分别创建 Engine/SessionLocal，模块组合后会增加连接数，并产生不必要的事务边界差异。

处理：`main.py` 改为复用 `app.database` 的 `engine`、`SessionLocal` 和 `get_db`，保留原导入名称兼容测试与其他模块；统一连接池启用 `pool_pre_ping` 和 300 秒 recycle。

### 4. CORS 配置组合无效

原配置同时使用通配来源和 `allow_credentials=True`。浏览器标准不允许凭证响应使用通配来源，且当前工作台使用同源与 Bearer 头，不依赖跨域 Cookie。

处理：保留兼容的通配来源，将 `allow_credentials` 关闭。后续启用 Cookie 登录时必须改为明确来源白名单。

### 5. 仓库当前版本存在重复的业务凭证样例

旧版静态服务清单、废弃 Compose 示例、历史备份和未挂载旧路由中存在明文密码或固定密钥值。

处理：旧静态清单中的具体账号密码已清空，Compose 改为环境变量占位；未挂载旧路由不再写入固定本机密码。

重要限制：Git 历史仍可能保存旧值。相关账号、数据库密码和 JWT 密钥必须在各自系统中轮换；如需从历史彻底清除，应单独安排受控的仓库历史重写，不在常规发布中执行。

## 已确认但本期不直接改动

### P0：管理界面默认免登录

`OPS_AUTH_ENABLED` 当前默认关闭，管理接口依赖在该模式下返回虚拟管理员。管理网段内任何能访问后端的客户端都可能调用写接口。

建议：单独实施认证恢复版本，先补齐登录、令牌签发、前端会话和回滚通道，再启用认证。不能只在生产环境直接切换开关，因为当前 `User` 模型已移除，旧鉴权路径需要重新设计。

### P0：运行配置仍带开发期默认凭证

`config.py` 仍为数据库、JWT、管理员密码和凭证加密键提供开发期默认值。直接删除默认值可能导致当前 systemd 环境漏配时无法启动，或使已有密文不可解密，因此本次发布不做未经验证的强制切换。

建议：先在生产主机以“只校验变量是否存在、不读取值”的方式确认四项均已注入并备份 `CREDENTIAL_KEY`，再把生产启动改成缺项 fail-fast；测试环境改用独立固定测试值。JWT 与管理员密码可轮换，`CREDENTIAL_KEY` 不得直接轮换，必须先完成密文迁移。

### P0：SSH 凭证仍存放在 `servers.ssh_key`

密码使用特殊前缀、私钥使用原文保存，与数据库实例和服务广场凭证的 Fernet 加密方式不一致。

建议：新增独立密文字段与凭证版本，双读迁移、验证所有主机连接后再清除旧字段。不得直接修改 `CREDENTIAL_KEY`，否则已有加密凭证无法解密。

### P1：启动期迁移失败后继续运行

`_ensure_new_columns()` 捕获迁移异常后只打印日志。数据库列缺失时应用仍会启动，随后在业务请求中出现 500。

建议：拆分“允许降级的可选迁移”和“必须成功的核心迁移”；核心 schema 校验失败时健康接口返回 not-ready，并阻止 Jenkins Verify 通过。

### P1：后台任务缺少统一生命周期管理

启动事件直接创建多个无限循环任务，没有统一保存任务句柄、关闭信号和任务存活状态。某个循环异常退出后缺少集中可见性。

建议：迁移到 FastAPI lifespan，统一注册、取消和报告后台任务状态；在 `/api/v2/health` 与 AI summary 中增加任务存活信息。

### P1：聚合查询存在数据规模风险

部分健康和指标聚合会把时间范围内全部记录加载到 Python。服务数、采样频率或保留周期扩大后，延迟和内存占用会线性增长。

建议：继续迁移为 SQL 聚合、每服务最新记录子查询和明确的最大时间范围。AI API 已采用分组最新指标查询与列表上限。

### P2：主程序和兼容前端体积过大

`main.py` 超过 4,000 行，并保留未挂载的旧 router、旧前端和历史备份。重复模型与接口容易在后续维护中产生分叉。

建议：先增加路由契约测试，再按服务器、服务、告警、报告和终端逐模块迁移；每次只迁移一个域，禁止一次性重写。

### P2：时间处理仍大量使用 naive UTC

Python 3.13 已对 `datetime.utcnow()` 给出弃用警告。当前数据库字段和前端均按无时区 UTC 约定工作，直接混改会导致比较错误。

建议：增加统一时间工具和兼容序列化，先处理新增模块，再逐表迁移为 timezone-aware UTC。

## v4.6.2 发布门槛

- AI API 缺密钥和无效密钥必须返回 401。
- AI API 响应不得包含 password、ssh_key、private_key、agent_token、key_hash、secret_ciphertext。
- AI API 请求不得调用网络探活、SSH、Docker 或 Agent。
- 主机指标查询不得按主机逐条执行最新指标查询。
- 现有后端测试和新增测试全部通过；前端生产构建通过。
- OpenAPI 包含 6 个 `/api/v2/ai/*` 路由且版本正确。
- GitLab、GitHub、Jenkins 与线上提交一致，发布结论等待流水线和线上验收完成。
